# 0.2.0 公开服务请求预算与协议瘦身

> 状态：设计稿，2026-11-25。目标不是“再加一个接口”，而是把同步从
> **逐会话拉清单** 改成 **一次发现 + 只取变化**，让公益服在 WAF 后面的
> 请求数、请求体和带宽可控。
>
> 关联：[MANIFEST-SLIMMING-DESIGN.md](MANIFEST-SLIMMING-DESIGN.md)、
> [ATTACHMENT-SYNC-SERVER-API.md](ATTACHMENT-SYNC-SERVER-API.md)、
> [PROTOCOL.md](../architecture/PROTOCOL.md)、[ROADMAP.md](ROADMAP.md)。

## 1. 目标

1. 稳定状态下，一个同步周期只产生 **1 次发现请求**，不为每个会话单独拉 manifest；
2. 只有真正变化的会话才读取批次引用和密文；
3. 发现响应和批次分页都有明确的大小上限；
4. 减少重复前缀校验和重复 manifest；
5. 所有流量能通过常见 WAF：标准 HTTP、短 URL、标准认证头、可处理 413/429/5xx；
6. 旧 0.1.6 插件仍能工作；新插件在旧服务端上回退。

非目标：

- 不在本轮做帧表迁移（MANIFEST 文档已明确 P2 后置）；
- 不做多租户、公益服计费和管理面板；
- 不改变端到端加密和 append-only 链语义。

## 2. 当前请求路径

现场观察：单人使用、70 多个会话时，一轮同步会出现 70 多次逐会话请求，
并且某些清单响应包含整条批次哈希列表。需要先埋点确认分布，但主要路径已经明确：

| 路径 | 现状 | 问题 |
|---|---|---|
| `GET /v2/sessions` | 一次分页快照，15 秒缓存 | 只解决“有哪些会话”，不解决“哪些变了” |
| `GET /v2/sessions/:id/summary` | 已有 head-only 摘要 | 客户端还没有把它作为主路径 |
| `GET /v2/sessions/:id/manifest` | 返回全部批次引用 | 每会话一次；大会话 170 KB 级 |
| `GET /v2/sessions/:id/batches` | 已有分页 | 客户端没有统一使用 |
| `POST /v2/sessions/:id/append` | 每会话一次追加 | 合理，但前面不应为它再拉全量清单 |
| `verifySharedPrefix` | 必要时重算全前缀 | O(帧数) 流量/CPU，重复发生 |

关键结论：

- `/v2/summary` 和 `/v2/batches` 已经存在，**第一阶段可以只改插件**，
  把 manifest 全量读取替换掉；
- 但要消除 70 多次“发现”，必须增加**跨会话的变更发现接口**；
- 清单的批次引用应分页，不要让发现响应携带全部哈希。

## 3. 目标请求预算

以 70 个会话、其中 0 个变化为例：

| 场景 | 当前 | 0.2.0 目标 |
|---|---|---|
| 稳态无变化 | 1 次列表 + N 次逐会话清单 | **1 次 changes，0 次 manifest/batches** |
| 1 个会话变化 | 列表 + 清单 + 批次 | **1 次 changes + 1 次 batches** |
| 首次 bootstrap | 列表 + 逐会话清单 | 1 次快照 + 每会话按需 batches |
| 70 个会话全部变化 | 70+ 清单 | 1 次 changes + 按需 batches；必要时再评估批量 batches |

建议验收阈值：

- 稳态发现响应 ≤ 32 KiB 未压缩、≤ 8 KiB gzip；
- 单会话 head summary ≤ 2 KiB；
- batches 单页默认 ≤ 100 条、≤ 64 KiB；
- 稳态一轮客户端请求数 ≤ 2（发现 + 健康/租约）；
- 单会话变化一轮 ≤ 4（发现 + 批次 + 必要时 blob）；
- 旧插件在 0.1.6 兼容路径上不增加 manifest 请求。

## 4. 协议设计

### 4.1 变更发现：`GET /v2/changes`

```text
GET /v2/changes?cursor=<opaque>&limit=200
```

响应只带“发现”需要的信息，不带批次引用：

```json
{
  "changes": [
    {
      "sessionId": "session-...",
      "revision": 1234,
      "kind": "append",
      "createdAt": 1794048068541,
      "formatVersion": 4,
      "lastSeq": 69590,
      "headChainHash": "...",
      "batchCount": 1510,
      "safeThroughSeq": 69590,
      "tailOpen": false,
      "workspaceKey": "...",
      "parentSession": null,
      "origin": null,
      "delegationDepth": 0
    }
  ],
  "nextCursor": "opaque-or-null",
  "hasMore": false,
  "highWater": 1240,
  "stale": false
}
```

规则：

- 按 `revision` 升序；
- `nextCursor` 只推进到本页最后一条；
- `stale: true` 表示游标早于保留水位，客户端退回快照；
- `kind` 至少覆盖 `append/delete/archive/restore/remove/reset`；
- 发现响应不返回 `batches`，不返回 `blobSha256`；
- 每页有硬上限（建议 200 条 / 32 KiB）；
- 支持 `ETag` 或空页，让无变化轮次尽量小。

服务端数据：

```sql
CREATE TABLE session_changes (
  revision INTEGER PRIMARY KEY,
  dataset TEXT NOT NULL,
  session_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  at INTEGER NOT NULL,
  kind TEXT NOT NULL,
  last_seq INTEGER,
  head_chain_hash TEXT,
  batch_count INTEGER,
  format_version INTEGER,
  safe_through_seq INTEGER,
  tail_open INTEGER,
  workspace_key TEXT,
  parent_session TEXT,
  origin TEXT,
  delegation_depth INTEGER
);

CREATE TABLE device_cursors (
  device_id TEXT PRIMARY KEY,
  revision INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

保留与水位：

- 水位 = `min(存活设备游标, 30 天前 revision)`；
- 清理水位以下的 changes；
- 吊销设备时删除/排除其游标，否则一台离线设备钉死水位；
- 清理任务每天一次，管理台可手动触发；
- 记录只保留计数/水位审计，不保留内容。

### 4.2 会话快照与摘要

保留：

```text
GET /v2/sessions?limit=&cursor=       # bootstrap，只含 head/summary
GET /v2/sessions/:id/summary         # 单会话 head，ETag
```

要求：

- `/v2/sessions` 不返回 `batches`；
- 摘要字段沿用现有 `V2SessionSummary`：
  `lastSeq/headChainHash/batchCount/formatVersion/workspaceKey/tailOpen/safeThroughSeq`；
- `revision` 可用于判断发现结果和摘要是否同一代；
- 支持 `If-None-Match` 304。

### 4.3 批次引用分页

```text
GET /v2/sessions/:id/batches?from=0&limit=100
   &expectedManifestDigest=<64hex>
```

规则：

- 只返回一页 `{index,seqFrom,seqTo,chainHash,blobSha256,...}`；
- `limit` 有硬上限；
- `expectedManifestDigest` 不一致返回 `409`，避免分页途中学到旧链；
- 客户端按需翻页，不在发现阶段抓全量；
- 响应头支持压缩。

### 4.4 增量前缀校验

客户端 receipt 升到 v2：

```json
{
  "receiptVersion": 2,
  "verifiedThroughSeq": 69586,
  "remoteBatchCount": 1510,
  "verifiedAt": 1794728311532
}
```

稳态：

1. changes 的 `headChainHash` 与 receipt 相同：不校验、不拉 manifest；
2. 变了：只取 `from = verifiedThroughSeq` 附近到头的 batches；
3. 校验重叠帧和新帧，更新 receipt。

全量校验只在：

- 没有 receipt；
- `formatVersion/createdAt/workspaceKey` 不一致；
- 本地文件变小或被重写；
- `replace`；
- 游标过期；
- 用户显式要求。

服务端可选提供：

```text
GET /v2/sessions/:id/chain?from=&limit=
GET /v2/sessions/:id/chain-digests?block=64
```

用于不回全 manifest 的全量校验；`/chain` 可先落地，摘要后补。

### 4.5 批量接口是否必要

先不要提前做。只有在埋点证明“70 个会话同时变化”仍是主要成本时，再加：

```text
POST /v2/sessions/batch-summary
   { sessionIds: [...] }
→ { summaries: [...], missing: [...] }
```

或一次性批次引用批量接口。批量接口会放大 WAF 的请求体风险，必须设置
ID 数量、响应字节和超时上限；不要在 0.2.0 第一阶段引入。

### 4.6 请求体控制

- 发现、摘要、批次读取都是 `GET`，没有请求体；
- 推送一个会话只发送**本次新增帧**，不重发旧帧引用或整条链；
- 帧内容继续 zstd，blob 继续走二进制批量上传，不做 JSON base64；
- 单次 append 的 `batchEvents` / `batchBytes` 保持显式上限；
- 不为“预检”额外发 POST；发现结果已经足够决定是否 append；
- 客户端不应在 query 里携带会话 id 列表；批量接口未来若存在，也限制 ID 数；
- 服务端对超限请求返回 JSON 413，客户端按错误分类处理；
- WAF 前置时，实际 body 上限要低于 WAF 的拒绝阈值，由部署配置保证。

## 5. 客户端行为

### 5.1 同步循环

```text
每轮：
  1. 读取本地 changesCursor
  2. GET /v2/changes
  3. 与本地 receipt/plan 合并
  4. 无变化 → 结束
  5. 有变化 → 只对变化会话取 batches
  6. 需要写入 → append
  7. 成功消费后持久化 newCursor
```

- 同一时刻只允许一轮同步；
- 手动同步可跳过节流，但仍受单轮上限；
- 自动同步默认 60 秒，加 0–20% 抖动；
- 429/5xx 指数退避，尊重 `Retry-After`；
- 页面隐藏/无网络时暂停；
- 不在启动时对每个会话发 manifest。

### 5.2 兼容旧服务端

- changes 能力缺失 → 回退 `/v2/sessions` 快照 + summary/batches；
- `manifest-head` 缺失 → 使用 `?batches=1` 或旧 manifest；
- 旧服务端没有 `/v2/changes` 时不发请求；
- 旧插件仍走原路径，不受影响。

### 5.3 请求合并

- 发现请求和摘要请求共享 `revision`，避免重复；
- 同一会话同一 head 的 batches 结果按 `manifestDigest` 缓存；
- blob 下载走批量接口，继续限量；
- 不要为了“顺手校验”拉全量 manifest。

## 6. WAF 与公益服

目标：所有请求都能通过常见反向代理/WAF，不依赖私有协议。

### 6.1 流量形状

- 只用标准 HTTP 方法：读 `GET`，写 `POST`；
- token 放 `Authorization: Bearer`，不放 URL；
- cursor 不透明、短（建议 ≤ 512 字符）；
- 路径参数只使用 URL-safe session id；
- 请求体 `application/json`；批量 blob 用现有二进制 content-type；
- 每个请求带 `X-Request-Id`（客户端生成或服务端返回），日志可追踪。

### 6.2 限流与配额

- 按设备 token + IP 双层限流；
- 默认目标：同步发现 ≥ 15 秒一次；手动同步除外；
- 超限返回：

```http
429 Too Many Requests
Retry-After: 30
```

- 客户端指数退避 + jitter，不立即重试；
- 单设备并发同步 1；
- 请求体超限返回 JSON 413，不返回 HTML；
- WAF 自己的 403/413/429 也要被客户端识别为可重试/不可重试错误。

### 6.3 缓存与安全

- 设备 API 默认 `Cache-Control: no-store`，避免 WAF/代理缓存带认证响应；
- 只有无认证的公开探测（如 `/health`）可短缓存；
- 不把 token、明文、附件内容写 URL；
- 响应压缩由服务端/反代处理，优先 gzip/br；不假设 WAF 支持自定义 zstd content-encoding；
- HTTPS 终止在反代；服务端信任 forwarded headers 时要显式配置。

### 6.4 观测

服务端记录：

- 请求数/字节数按 endpoint；
- 429/413/5xx；
- changes 游标落后、stale 次数；
- 每设备每轮请求数；
- 慢查询和 DB 大小。

客户端记录：

- 每轮请求数、请求体/响应体、耗时分位；
- 同一会话 head 重复读取次数；
- 回退旧协议次数。

## 7. 实施阶段

### P0：基线埋点（不改 wire）

- 客户端请求计数器：按 endpoint 统计次数/字节；
- 复现“70 多请求”的具体来源：summary 元数据 fallback、push、pull、attachment；
- 服务端访问日志结构化；
- 固化 3 个真实场景：70 会话无变化、1 会话变化、首次 bootstrap。

### P1：插件停用全量 manifest（不升协议）

- `readRemoteSessionMeta` 改用 `/summary`；
- push/pull 使用 `/summary` + `/batches?from=&limit=`；
- `verifySharedPrefix` 只在 receipt 失效时执行；
- 保留旧服务端回退；
- 这一阶段不需要服务端 schema 变更，可以独立发插件版本。

### P2：changes v3（服务端 + 插件）

- schema 7：`session_changes`、`device_cursors`；
- `GET /v2/changes`；
- 水位、30 天保留、吊销游标清理；
- 客户端 `changesCursor` 持久化与 stale 回退；
- 快照响应带 `revision`。

### P3：增量校验与链摘要

- receipt v2；
- 增量 batches 校验；
- `/chain` 先落地，`/chain-digests` 后补；
- replace/生命周期变化清 receipt。

### P4：公开服务硬化

- 限流、413/429 文案、Retry-After；
- WAF 规则联调；
- 压缩与 HTTP/2；
- 访问日志、指标、告警；
- 压力测试：70/200/1000 会话，单设备/多设备。

### P5：按测量决定批量接口

- 只有 P0/P4 数据显示批量 request 是瓶颈时才做；
- 否则保持简单：changes + per-session batches。

### P6：附件索引清单与 peers 消费

- 附件索引清单端点；
- 插件版本矩阵使用 `/v2/peers` 过滤已吊销设备；
- 这两项可以和 P2–P4 并行。

## 8. 验收

- 70 会话稳态：≤2 个请求/周期，0 个 manifest；
- 1 会话变化：≤4 个请求，无全量哈希；
- 发现响应 ≤32 KiB 未压缩；
- batches 单页 ≤64 KiB；
- 旧插件连新服务端成功；
- 新插件连旧服务端回退成功；
- 429 含 `Retry-After`，客户端不风暴；
- WAF 前置下 413/429/超时均有明确错误与退避；
- schema 迁移自动备份、回滚脚本通过；
- changes 保留清理后 stale 客户端能重新 bootstrap。

## 9. 待拍板

1. changes 是短轮询还是带 `wait` 的长轮询；WAF 超时阈值要先实测；
2. 是否在 0.2.0 就删 `/manifest` 的稳态用途，还是只改默认形状；
3. 批量 batches 是否需要；先用 P0 数据决定；
4. 限流阈值：每设备每分钟多少请求，是否需要按 IP 额外限制；
5. 压缩放在服务端还是反代；是否允许 `zstd`；
6. 帧表 P2 是否确认继续后置（当前文档与附件设计存在冲突）；
7. 公益服是否要求账号/邀请码前置，还是只靠设备 token。

## 10. 不建议塞进 0.2.0

- 多租户、计费、管理后台扩展；
- 附件分片；
- 帧表迁移（除非先统一文档决策）；
- 压缩/保留策略之外的大规模重构；
- 自动升级/自动修复策略。
